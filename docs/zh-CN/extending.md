# 添加处理手册和故障场景

[English](../en/extending.md) · **简体中文** · [项目介绍](../../README.zh-CN.md)

当前可以通过资源文件扩展知识库和演示数据，无需修改 Java。
接入 Prometheus、日志平台等真实系统则需要编写适配代码，不属于添加样例文件的范围。

## 添加处理手册

在 `src/main/resources/knowledge/` 下新建 Markdown 文件。
内容应说明一类问题的常见表现、可能原因、验证方式和缓解方法，例如：

```markdown
# Runbook: database connection pool exhaustion

## Symptoms

请求延迟升高，连接池使用量持续接近上限。

## Possible causes

慢查询、长事务或连接未释放，都可能导致连接长时间被占用。

## Verification

对照变更时间，检查数据库查询耗时、事务时长和连接持有情况。

## Mitigation

根据验证结果，考虑回滚相关变更或处理长事务，并说明操作风险。
```

启动时，程序按 `## ` 二级标题切分文档，并在每个片段前保留文档标题和引言。
因此每节应尽量能独立理解。更改文件后重新运行 Maven、重启应用，内存索引会重新建立。

处理手册写通用排查方法。某个服务的字段单位、池容量和时区等信息，应写在该服务的 `profile.md`，
避免在多个手册里重复维护。

## 添加演示场景

每个服务对应 `src/main/resources/fixtures/` 下的一个目录，目录名就是查询使用的服务名：

```text
src/main/resources/fixtures/example-service/
├── profile.md
├── metrics.txt
├── logs.txt
└── changes.txt
```

| 文件 | 应包含的内容 |
|---|---|
| `profile.md` | 技术栈、字段含义、单位、时区、正常基线和依赖 |
| `metrics.txt` | 带时间戳的指标，包含正常时期和异常发展过程 |
| `logs.txt` | 与指标时间线对应的错误或异常日志 |
| `changes.txt` | 发布或配置变更，包括完整时间和改动说明 |

现有的 `checkout-service` 展示查询变慢后的连接池耗尽，`order-consumer` 展示无界缓存导致的消费积压。
可以参考这些文件的格式，但要让新场景的数据支持它自己的结论。

## 保持时间线一致

1. 确定预期原因和验证它所需的证据，再写数据。
2. 记录触发问题的变更时间，并让后续指标和日志呈现合理的异常发展过程。
3. 保留正常指标或其他反证，例如消费积压时生产速率稳定，帮助区分不同解释。
4. 在服务说明中写清单位、正常值和时区，不要直接填入预期诊断。
5. 配置相应处理手册，并准备几种不同问法，包括不提供服务名的提问。

时间过滤器识别完整日期与时间，例如 `2026-08-24 14:26:03.481` 或
`2026-08-24T00:06:44+08:00`，也能识别 JSON 日志字段中的时间戳。
无时区的时间按应用配置的 `default-zone` 解析；目前该配置对所有此类样例统一生效。
不要只写 `HH:mm`，跨午夜场景尤其需要完整日期。

服务列表在启动时通过 `*/metrics.txt` 发现目录，文件内容也会被缓存。
新增或修改场景后，应重新运行 Maven 并重启应用。
指标和日志按时间窗过滤，起点默认向前扩展一小时；变更记录不按时间过滤。

## 手动检查新内容

运行应用后，用 [API](api.md) 或网页查询新场景，检查：

- 服务是否出现在 `listServices` 的结果里，服务说明是否准确。
- 指标和日志能否在指定时间窗内返回，窗口外是否给出可用范围。
- `retrievedKnowledge` 是否包含相关处理手册。
- 报告引用的每条证据能否在工具结果或检索片段中找到。
- 对模糊提问和证据不足的情况，报告是否仍然合理。

模型结论可能随运行变化，手动检查不能替代评估集。
当前尚无诊断评估框架；新增场景时应同时记录预期原因、关键证据和不能据此推出的结论，
便于后续接入自动评估。
