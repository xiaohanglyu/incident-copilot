# 路线图

[English](../en/roadmap.md) · **简体中文** · [项目介绍](../../README.zh-CN.md)

项目已经能够用样例数据完成一次故障调查。接下来先评估诊断质量，再扩展调查流程、
审核与审计能力，最后接入真实系统。目标和范围见[项目介绍](../../README.zh-CN.md)。

## 已完成

- Spring Boot 后端、查询工具和结构化报告。
- 连接池耗尽、Kafka 消费积压两个样例场景。
- 服务说明查询，指标和日志的时间过滤。
- Markdown 处理手册的切分、本地向量化和检索。
- 使用 Gemma 的本地配置方式。
- 后端记录工具参数、返回结果和耗时。
- 中英文网页，以及通过 SSE 展示调查进度。

这些能力构成了可运行的演示，不代表已经验证了诊断准确率、定位效率或生产可用性。

## 后续阶段

| 顺序 | 阶段 | 预期结果 |
|---|---|---|
| 1 | 建立评估集 | 能比较不同模型、提示词和流程的表现 |
| 2 | 多轮调查 | 根据初步假设补充取数、重新检索，明确停止条件 |
| 3 | 补充服务上下文 | 展示可疑变更详情和服务负责人 |
| 4 | 审核、审计与数据保护 | 保存调查，记录审批，在模型输入前脱敏 |
| 5 | 接入真实数据源 | 查询监控、日志和发布系统 |
| 6 | 持久化知识库 | 支持持续更新处理手册和复盘经验 |
| 7 | 运行与成本控制 | 记录消耗、设置预算、追踪调用 |

## 1. 建立评估集

先把当前流程的表现记录下来，后续改动才有比较依据。

- [ ] 为每个场景记录预期根因、关键证据和所需数据来源。
- [ ] 加入模糊提问、不提供服务名和术语不准确的问法。
- [ ] 加入无关发布、上游故障和证据不足等场景。
- [ ] 补充从公开事故复盘改编的场景。
- [ ] 检查根因、证据支持程度、工具调用、手册命中和重复运行的稳定性。
- [ ] 记录耗时和模型消耗，对比同一模型不使用工具与使用当前流程的结果。
- [ ] 提供可重复执行的评估命令，用于检查提示词和模型变更。

评估还应收集实际 on-call 工程师的使用反馈。诊断耗时与 MTTR 分开衡量：
要验证恢复时间是否改善，需要观察人工核对、决策和执行恢复操作的完整过程。

## 2. 多轮调查

当前使用一次 `ChatClient.call()`，其中的工具往返由 Spring AI 管理。
后续计划由应用显式管理“收集证据、提出假设、补充调查”的过程。

- [ ] 保存候选原因及其支持和反对证据。
- [ ] 根据缺失证据发起补充查询，并重新检索处理手册。
- [ ] 返回有排序依据的候选原因，允许以证据不足结束。
- [ ] 设置轮次、token 和耗时预算。
- [ ] 用同一评估集比较新旧流程，检查准确率收益及额外成本。

## 3. 补充服务上下文

- [ ] 展示可疑变更的 diff 或配置差异。
- [ ] 提供服务负责人和升级联系信息。

## 4. 审核、审计与数据保护

- [ ] 持久化调查输入、工具结果、检索片段和报告。
- [ ] 将处理建议保存为可审阅的记录。
- [ ] 记录批准、否决、操作人和时间。
- [ ] 在工具结果进入模型前处理敏感数据。

审批针对建议，工具仍然只读。当前没有自动修复计划。

## 5. 接入真实数据源

- [ ] 指标工具接入 Prometheus。
- [ ] 日志工具接入 Loki，把关键词和时间条件转成 Loki 查询。
- [ ] 变更工具接入 GitHub 或发布流水线。
- [ ] 配置各数据源的凭证、时间范围和查询映射。
- [ ] 验证跨来源的时间与字段含义是否一致。
- [ ] 评估使用 OpenRCA 等数据集子集作为适配和外部评估来源的可行性。

尽量保持现有工具接口，减少模型编排层改动；真实系统的权限和接口限制需要在接入时验证。

## 6. 持久化知识库

- [ ] 评估使用 pgvector 替换内存向量库。
- [ ] 提供知识写入和更新接口，避免只能在启动时建立索引。
- [ ] 将已审核的故障处理经验整理后写入知识库。

## 7. 运行与成本控制

SSE 进度展示已实现，后续补充：

- [ ] 单次调查的 token、耗时和成本统计。
- [ ] 调查预算及超限处理。
- [ ] 跨模型请求和工具调用的链路追踪。
- [ ] 评估是否通过 MCP 向外部 agent 提供同一批只读工具。
